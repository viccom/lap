# 文字精准搜索：技术调研与 Lap 实测报告

日期：2026-11-12 ｜ 范围：Lap 图片理解标注的文本检索（F2 精确搜索）｜ 环境：Windows + MSVC，debug 库 404 张照片、40 条标注

## 0. 结论摘要

1. **单一方法不够，但也不需要一上来就上向量**：本任务上 **BM25 全文检索（混合 token）** 把 Recall@1 从 **0.273 提到 0.936**、未命中从 **80/110 降到 0**，延迟约 **7ms/查询**，完全本地。
2. **稠密向量（zhipu/embedding-3）单独用 Recall@1 0.927**，不优于 BM25；**RRF 融合没有超过 BM25**（0.955 vs 0.955）；**rerank 没有提升**（0.945）且多一次网络往返（首次约 200ms/查询）。
3. **LLM 查询扩展在本轮不可靠**（JSON 截断/超时频发），未带来指标收益；不建议现在接入。
4. 因此当前产品策略：**精确搜索 = BM25 排序召回**（已落地）；**语义搜索 = 图像向量**（保留，用于同义改写/跨模态）；不引入 API rerank 与查询扩展。
5. 排序检索无法“证明没有”：查询「摘葡萄的小女孩」仍会返回葡萄照片（词面高度重叠），要做负例拒绝需要实体级语义判断，BM25 分数阈值无法干净分离（负例最高分 24.5，正例最低分 11.9）。

## 1. 技术调研：当前主流做法

### 1.1 检索范式

| 路线 | 代表 | 优点 | 局限 |
|---|---|---|---|
| 稀疏/词面（BM25、FTS5） | Okapi BM25、SQLite FTS5 | 精确词、专名、短查询强；零模型成本；可解释 | 同义改写弱 |
| 稠密（双塔 embedding） | BGE-M3、Qwen3-Embedding、多语言 E5 | 语义/改写强 | 需要模型与向量存储；对专名/数字弱；有推理成本 |
| 混合 + 融合 | BM25 + dense + RRF | 兼顾词面与语义，工业默认 | 两路成本；融合权重需按域调 |
| 精排（cross-encoder） | BGE-reranker、Qwen3-Reranker、Cohere Rerank | 显著提升 top-k 精度 | 每候选一次模型调用；延迟/成本高；需先召回候选 |

**证据要点**：

- 2026 年的一项检索基准（BM25 → Corrective RAG）在多个数据集上观察到 **BM25 在每项指标上优于稠密检索，而混合 RRF 全场最佳**（arXiv 2604.01733）。这说明 BM25 不是“过时基线”，在短查询/专名/精确词场景仍是主力。
- RRF（Reciprocal Rank Fusion）由 Cormack 等提出，`score = Σ 1/(k+rank)`，k=60 是无参数默认值，对分数不可比的两路结果特别稳（SIGIR 2009）。
- Qwen3-Embedding / Qwen3-Reranker（2025-06）是当前中文/多语检索的强模型家族；reranker 作为 cross-encoder 精度高于 bi-encoder，但成本也高。
- BGE-M3 同时提供 dense / sparse / multi-vector，官方推荐“混合检索 + reranker”；这说明工业界的共识是**多路召回 + 精排**，而不是单模型包打天下。
- 生产环境的反例：一项企业 RAG 部署研究发现，**多查询/RRF 融合提升的召回在 rerank + 截断之后基本被抹平**（arXiv 2603.02153）；本地优先的 vstash 也报告 post-RRF 的 cross-encoder rerank 未能提升 NDCG（arXiv 2604.15484）。→ 融合与精排要看场景实测，不能默认“加了就更好”。

### 1.2 中文分词/索引

- 中文无空格，FTS5 的 unicode61 不切分 CJK；常见做法是**双字（bigram）切分**，工程上简单且效果稳定（社区实践：SQLite FTS5 7 行 bigram 修复）。
- 学术上，**双字索引与词索引效果相当，某些语料上更好**（Kwok, SIGIR'97：bigram “surprisingly well”，比 1-gram 提升约 17%；Nie & Ren, IP&M 1999：n-gram 与词相当）。
- **词 + 双字混合索引**在 BM25 下对短查询更有效（Luk & Wong, NTCIR）。
- 因此本项目的“双字 + 单字 + 拉丁词”混合 token 是有依据的，不需要引入分词词典依赖。

### 1.3 对本项目的映射

| 技术 | 本项目可用性 | 结论 |
|---|---|---|
| FTS5 + bigram/char | 已有（迁移 v24/v25） | 保留，改为 BM25 排序 |
| 稠密文本检索 | 网关 `zhipu/embedding-3` 可用 | 实测无增益，暂不引入 |
| 图像向量检索 | 已有 CLIP + 多语言文本模型 | 保留为“语义搜索” |
| RRF | 可用（本地） | 实测无增益，暂不引入 |
| Rerank | 网关 `zhipu/rerank` 可用，但分数压缩到 0.9999x | 实测无增益，暂不引入 |
| LLM 查询扩展 | 网关可用，但 JSON 不稳定 | 暂不引入 |

## 2. 原实现的问题

原 `t_fts::search` 是**过滤式**的：查询的每个双字都必须出现在同一列；全部失败后要求**每个单字**都出现。结果是：

- 关键词查询（`摘葡萄`）能中；
- 同义改写/自然句（`一个小男孩躺在草地上` vs 标注「…孩子仰面躺着…草地上…」）**零结果**；
- 评测中 110 条正例有 **80 条完全无结果**（Recall@1 = 0.273）。

这不是索引缺词，而是**“必须全部命中”的召回策略**问题。

## 3. 实测设计

### 3.1 语料与查询

- **语料**：debug 库 40 条真实标注（用户已有 4 条 + 批量新增 36 条），图片 404 张；每条文档 = caption + tags。
- **查询集 113 条**：
  - 96 条 LLM 生成（每篇 3 类：关键词 / 同义改写 / 自然句）；
  - 10 条**硬改写**（人工构造，禁止复用原文连续两字，如「小孩在藤架下举着一挂青提」→ 葡萄照片）；
  - 7 条用户真实查询/负例（含「一个小男孩躺在草地上」「摘葡萄的小女孩」「飞机在跑道上起飞」「海边冲浪的女孩」）。
- **相关性标签**：单目标（generated 查询确保指向该照片）；负例 target=None。
- **指标**：Recall@1/3/5、MRR@10、nDCG@10、未命中数、平均延迟。

### 3.2 对比方法

1. `current_fts`：原产品逻辑（双字 AND → 单字 AND）
2. `bm25_bigram`：仅双字 token 的 BM25
3. `bm25_char`：仅单字 token 的 BM25
4. `bm25_mixed`：双字 + 单字 + 拉丁词的 BM25（k1=1.2, b=0.75）
5. `dice`：字符双字集合相似度排序
6. `dense`：`zhipu/embedding-3` 余弦
7. `rrf_bigram_dense`、`rrf_bm25_dense`：RRF(k=60) 融合
8. `dense_rerank`：dense top-10 → `zhipu/rerank`
9. `expand_bm25`：LLM 生成同义词后 BM25
10. **产品实现**：Rust `t_fts::search`（BM25 OR + 列权重 + 短查询保护），通过真实命令 `search_fts` 回放 113 条查询。

### 4.4 可选：云端 LLM 视觉重排（筛选，而非全排列）

用户实测“结果包含目标但匹配度不高”。第一版把查询 + 20 条标注发给 `auto/deepseek-v4.1-flash`，要求对**所有**候选排序；结果第 1 名正确、其余与描述无关。原样回放显示模型返回的正是候选输入顺序（只把目标挪到首位）——**候选池是 BM25 词面召回，强制全排列必然留下无关项**；请求也只发了标注文本，没有画面。

改为**视觉筛选**：每个候选取 512px 缩略图 + 编号发给（设置页配置的）多模态模型，提示词要求只返回画面确实符合的编号，没有符合返回 `[]`；显式属性（性别/人数/颜色/地点）必须相符，缺少次要道具不算不符。

| 用例（编译后的真实命令） | 候选 | 返回 | 耗时 |
|---|---|---|---|
| 小男孩玩滑板车累了，躺在草地上休息 | 精确 top-20 | `[101]` | 3.0s |
| 摘葡萄的小女孩（负例） | 6 张葡萄/男孩照 | `[]` | 1.9s |
| 同上（语义 top-7） | 7 张 | `[101]` | 1.6s |
| 生日蛋糕 | 8 张（含葡萄照） | 6 张蛋糕照 | 1.9s |
| 穿红色衣服的人在雪地里 | 5 张 | `[37]` | 2.0s |

结论：把“全排列”改成“筛选”后，无关尾部消失，负例拒绝成立；代价是每候选一张缩略图（约 1MB/20 张）发送到网关、每次 1.6–3.5s。旧 76 条查询的排序指标（R@1 0.921→0.961）衡量的是全排列模式，新模式的指标语义不同，不再沿用。

## 5. 分析

1. **“过滤”是根因**：旧逻辑把“查询词必须齐全”当召回条件，任何措辞差异都会导致零结果；改成“按命中词的相关度排序”，同义/自然句立刻可用。
2. **BM25 足够强**：在 40 篇同质语料上，BM25 混合 token 与稠密向量打平甚至更好；短文本（caption 30-80 字）场景尤其如此。
3. **稠密向量不是没价值，而是没有增量**：dense 0.927 vs BM25 0.955，且多 9ms/次网络调用；RRF 融合仅让 MRR 微增（0.974→0.977），R@1 不变。
4. **cross-encoder API rerank 不划算，LLM 视觉筛选可选**：`zhipu/rerank` 0.945（比 dense 还低，分数全部 0.9999x），每次 +200ms，不做默认；但让多模态 flash 模型看 top-20 缩略图、只保留画面确实相符的候选，能消除“第 1 名正确、其余无关”的尾部并支持负例拒绝（`摘葡萄的小女孩` → `[]`），每次 1.6–3.5s，适合作为**默认关闭的勾选项**。
5. **查询扩展不可靠**：LLM 输出 JSON 截断/超时，且即使成功也没有指标收益。
6. **负例拒绝是另一问题**：词面检索天然会给“部分匹配”的结果；`摘葡萄的小女孩` 与葡萄照片共享 `摘葡萄`，BM25 必然高分。分数阈值不可行（负例最高 24.5 > 正例最低 11.9）；要做拒绝需要实体级判断（如 cross-encoder + 校准，或 LLM 判定），不应由 BM25 承担。
7. **短查询保护是必要的**：产品测试发现 2 字人名「小明」在加入单字 token 后会命中「小红」；限制“≥3 个汉字才加单字 token”后，长句收益保留、短名精确性恢复（由 `fts_hook_tests` 捕获）。

## 6. 建议（按优先级）

1. **保留当前实现**：精确搜索 = BM25（混合 token + caption×5），零网络、7ms、R@3=1.0；UI 已加说明“按相关度排序，允许部分命中”。
2. **可选 LLM 视觉筛选**：已实现为默认关闭的勾选项，把 top-20 候选的缩略图与查询一起发给设置页配置的多模态模型，只保留画面确实相符的候选；无关尾部消失、负例可拒绝，代价 1.6–3.5s/次。默认路径保持纯 BM25。
3. **暂不接入 cross-encoder API rerank / LLM 查询扩展**：`zhipu/rerank` 无增益且 +200ms；查询扩展 JSON 不稳定。若未来要接，先在本评测集上证明增益，再考虑默认开启。
4. **语义搜索继续独立存在**：图像向量用于“说法完全不同/跨模态”的场景，不要与 BM25 混成一个黑盒。
5. **未来升级路径**（语料 >5k 或跨主题时再评估）：
   - 本地文本 embedding（BGE-M3 / Qwen3-Embedding-0.6B ONNX）建标注向量，BM25 + dense + RRF；
   - 两者都必须先用本目录的评测脚本回归，避免“凭感觉加模型”。
6. **负例拒绝**单独设计：如果需要“明显不匹配就不返回”，用 rerank/LLM 判定 + 人工校准阈值，不要用 BM25 分数硬切。

## 7. 复现

```bash
cd lap/docs/dev/search-eval

# 1) 构建语料与查询（需要网关；会写入 corpus.json / queries.json）
LAP_VL_GATEWAY_URL=http://192.168.199.8:3425 \
LAP_VL_API_KEY=... python build_eval_set.py --generate

# 2) 方法对比（写入 results.json、embeddings.json、reranks.json、expansions.json）
python run_eval.py

# 3) 产品实现回放（需运行中的 dev 应用与 CDP 9222；写入 product_ranks.json）
node docs/dev/search-eval/product_replay.mjs   # 见同目录脚本（node 版）
```

说明：`queries.json`、`queries_hard.json`、`corpus.json` 已随仓库保存，可直接复跑指标；`embeddings.json` / `reranks.json` / `expansions.json` 为缓存，删除后会重新请求网关。

## 8. 局限

- 语料仅 40 条标注 / 404 张照片，query 主要由 LLM 从 caption 生成，存在词面偏置；硬改写只有 10 条人工样本。
- 相关性是单目标二值，未标注“部分相关”（如两张葡萄照片可能都相关，`摘葡萄的小男孩` 目标排第 2 未必是错误）。
- 只覆盖一个模板（内置描述 v1）与中文；其他语言/模板未评测。
- 产品索引还包含未标注照片的文件名/元数据，评测只统计 40 篇标注文档的相对排名。
