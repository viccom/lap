## 4. 合并里挖出的两个真问题

1. **聚合门禁是假绿的**：runner 用 `spawnSync(npm_execpath, …, {shell:true})` 拉起各域，Windows 上 cmd.exe 不执行 `npm-cli.js`，**每个域秒退 0**，门禁报「35/35 全绿」而一个测试都没跑。是本次用「单文件直跑」对出来的（`node --test tests/offlineCatalog.test.mjs` 直接红）。
   修法：runner 直接 `spawn(process.execPath, args)`；并新增 `tests/aggregateRunner.test.mjs`（`test:gate`）钉住「失败域必须让 runner 退出 1」「域脚本必须真的被执行」。
2. **上游改动打脸 fork 的测试**：`a6ce653c` 在 `album-accessibility-changed` 处理里加了 `markSimilarCandidatesChanged()`，fork 的 `offlineCatalog.test.mjs` 抽取该处理函数在沙箱里求值，缺这个依赖 → ReferenceError。补依赖即可（不是产品 bug）。

## 6. 经验

- 类型基线为 0 的门禁，在每次上游同步时都会自动变红一次——**这正是基线制门禁的价值**，修法与既有套路一致（JS store 的 `null` 默认值要 JSDoc 标注）。
- **门禁本身要能红**。任何「汇总型」脚本都要配一个自检（`test:gate` 就是聚合 runner 的自检）。
- 上游改了被抽取的函数体，fork 的「抽取式」测试就会漂移——这类测试要跟着上游契约补依赖，而不是删断言。
