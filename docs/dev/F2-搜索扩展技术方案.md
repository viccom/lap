# F2 · 搜索扩展（精确档 FTS5 + 语义档强化）技术方案与实施计划

> 状态：草案 v1（2026-11-11）· 分支 `develop` · 前置：F1 完成（精确索引要吃 VL 描述）；本方案与 F1 无代码交叠，可并行开发纯索引部分。

## 1. 目标与非目标

**目标**
- **保留** lap 现有全部搜索方式，行为不变：文件名/EXIF LIKE、CLIP 向量语义、相似图、smart tags。
- **新增精确档**：FTS5 全文检索，覆盖文件名/注释/EXIF 标题/标签/人名/相机/地点/VL 描述；**中文双字切分**（自研，零词典依赖）——解决「过年」「生日」这类中文词在 LIKE 下不可搜、在多语言 CLIP 下分数不稳的问题。
- **新增统一档位 UI**：搜索框旁「精确 / 语义 / 全部」三档；「全部」= 现状（两路并行）。
- **写入即检索**：FTS 文档在数据写入的同一事务内更新，无后台 reindex 延迟。

**非目标**
- 不替换/重写现有向量搜索；不做搜索结果精排（Argus rerank 留作后续可选增强）；不改现有 SQL 的排序语义。

## 2. 基础设施事实（已验证）

- rusqlite **bundled 构建默认启用 FTS5**（libsqlite3-sys build.rs 固定 `-DSQLITE_ENABLE_FTS5`，另有 FTS3/JSON1/RTREE）——无需改任何构建配置。**F0 构建跑通后补一次运行时 probe 双保险**（`CREATE VIRTUAL TABLE temp.t USING fts5(content)`）。
- 中文双字切分：从 homepix 移植算法逻辑（纯 Rust 实现：UTF-8 遍历，CJK 连续段滑窗成 bigram，ASCII 段整词 lowercase），零外部依赖。
- 现有文本 LIKE 搜索位置：t_sqlite.rs:5339-5355（`get_query_files`）——**不改它**，精确档是新增并行路径。

## 4. 设计决策

- **不用触发器**（SQLite FTS 外部内容表常用手法），改用 Rust 层显式钩子：lap 的事务纪律（每写点已在事务内）让显式调用与数据写入同事务原子；触发器对 lap 的 22 处事务点不可见、调试困难，且上游改 SQL 时触发器会静默失效——显式钩子缺失会被编译器抓到（调用点删除时 import 报警）。
- **FTS 表结构**：`files_fts(file_id UNINDEXED, content, aux)` 外部内容模式（content 无索引 bloat），`content` = 空格连接的：name / name_pinyin（**现成列**，中文拼音可搜是白捡的能力）/ comments / e_title / e_artist / tags（查 afile_tags 拼装）/ person names / camera make+model / geo_name+admin1 / VL 标注文本。aux 列存 JSON 便于调试展示命中来源。
- **查询侧**：用户输入经同一 `tokenize_cn` 切分 → `"tok1" AND "tok2"`…（FTS5 phrase 查询）；单字降级 LIKE（沿用 homepix 经验：bigram 无法命中单字）。
- **`files_fts` 的 docid = file_id**，删除即 `DELETE FROM files_fts WHERE file_id=?`。

## 6. 与上游同步的兼容性预算

- t_sqlite.rs 5 个锚点是最大冲突面：上游若重排 `add_to_db` 等，rebase 时按矩阵表逐一复核钩子仍在事务内——**矩阵表就是 rebase checklist**。

- 上游新增表/字段（如新 EXIF 列）→ `build_doc` 单点扩展 + 测试补充，无迁移冲突。

### 7.6 查询放宽：双字严格 → 单字兜底（2026-11-12）

**问题**：查询侧把所有相邻双字按 AND 要求出现在同一列，跨词双字（如「摘葡萄的小男孩」里的 `萄的`、`的小`）在文档里几乎不存在，导致内容明明匹配却零结果。

**实现**（`t_fts.rs`）：
- 索引同时写入双字与单字（`index_text` = `tokenize` + `relaxed_tokens`），单字只用于兜底；
- `search` 两段式：先按双字/整词 AND 严格匹配；**仅当严格结果为空**且查询含 CJK 时，用「全部单字 + 全部整词」AND 再查一次；
- 迁移 **v25** 对已有库重建索引（旧索引没有单字 token）。

**效果**（真实标注数据，caption「一个小男孩在葡萄园里采摘葡萄…」）：

| 查询 | 严格段 | 放宽段 | 结果 |
|---|---|---|---|
| 葡萄 | 命中 | — | 命中 |
| 摘葡萄 | 命中 | — | 命中 |
| 摘葡萄的小男孩 | 未命中（缺 `萄的`/`的小`） | 全字符在场 | **命中** |
| 摘葡萄的小女孩 | 未命中 | 缺「女」 | 无结果（符合预期） |

边界：放宽段要求查询的**每个字符**都出现，不做停用字过滤；字面量语义为主，不引入词表或模型。

### 7.7 实验台增加「语义搜索」（2026-11-12）

**问题**：用户查询「一个小男孩躺在草地上」，标注原文是「…**孩子仰面躺着**…草地上…」——同义改写（小男孩 vs 孩子），任何字面匹配都无法命中，精确搜索返回 0 是正确行为但不是用户预期。

**做法**：实验台 F2 区在「精确搜索」旁增加「语义搜索」按钮，走已有的图像向量检索（`search_similar_images`，CLIP 类 embedding + 余弦 + 阈值），结果按相关度排序并标 `#1..#N`；精确搜索保持原语义不变。中文查询检测到 CJK 时：若已安装多语言文本模型则**仅在内存中**切到它（不改设置），未安装则提示去「设置→搜索」下载。

**实测**（debug 库 404 张）：
- 精确：`一个小男孩躺在草地上` → 0 命中（字面不匹配，符合设计）
- 语义：同查询 → 12 命中（阈值 0.26），目标 `A (1).jpg` 排 **#3**
- 默认英文模型下同查询结果完全无关（目标不在 33 条内）→ 中文必须多语言模型，UI 已自动处理并给提示。

代价：语义档依赖本地向量模型与已有 embedding，阈值来自设置（默认 Standard）；中文语义能力受多语言模型质量限制，排序不等于精确召回。

### 7.8 精确搜索改为 BM25 排序召回（2026-11-12）

**背景**：7.6 的双字/单字放宽仍要求“每个 token 都命中”，同义改写（`小男孩` vs `孩子`）与自然句零结果。调研 + 113 条查询实测（详见 `docs/dev/SEARCH-RESEARCH-2026-11-12.md`）显示：**过滤式 AND 的 Recall@1 仅 0.273、110 条正例中 80 条无结果；BM25 排序召回 0.955/零未命中**。

**实现**（`t_fts.rs`）：
- 查询 token = 双字 + 拉丁词；当查询含 **≥3 个汉字**时再追加单字 token（短名保持双字精确：否则「小明」会经单字「小」命中「小红」，由 `fts_hook_tests` 捕获）；
- 单条 FTS5 MATCH：所有 token **OR**，`ORDER BY bm25(files_fts, 1,1,1,1,5) LIMIT n`（caption 权重 5，实测 0.909→0.936 Recall@1；name 加权无收益）；
- 命中列徽标：对返回的 file_id 再跑 5 个按列 OR 查询（仍复用同一索引，不额外建表）；
- 单汉字查询保留 LIKE 兜底；索引结构不变（v25 已含双字+单字），无需迁移。

**产品回放（真实 `search_fts` 命令，113 条查询）**：R@1 **0.936** / R@3 **1.000** / MRR **0.964** / 未命中 **0** / 约 **7ms**。

**语义变化（需知悉）**：
- 精确搜索现在是**排序**而非过滤：部分命中的照片会以低名次返回，不再“缺一个词就零结果”；
- 负例（`摘葡萄的小女孩`）仍会返回葡萄照片——词面高度重叠，BM25 分数无法干净拒绝（负例最高 24.5 > 正例最低 11.9）；需要拒绝能力时应另设 rerank/LLM 判定并校准，而不是收紧 BM25；
- UI 已在搜索框下增加说明：「精确搜索 = 全文检索：按相关度排序，允许部分关键词命中」。

**未采纳（实测无收益）**：`zhipu/embedding-3` 稠密检索（R@1 0.927）、RRF 融合（0.955，与 BM25 持平）、`zhipu/rerank` cross-encoder 精排（0.945，且 +200ms/次）、LLM 查询扩展（JSON 不稳定、无增益）。

### 7.9 可选「云端 LLM 重排」= 按图片描述筛选（2026-11-12）

用户反馈「结果包含目标但匹配度不高」：勾选重排后第 1 名正确，第 2–20 名却与描述无关。排查确认根因不在模型能力，而在**请求姿势**：

- 第一版只把「查询 + 20 条标注文本」发给模型，提示词要求「**对所有候选编号排序、不要遗漏**」。同一批候选原样回放下，模型返回的正是 `[101,35,36,29,24,23,21,14,13,37,2,1,8,7,19,20,15,16,5,6]`——与界面顺序逐位一致，即模型只把目标挪到第 1 位，其余原样回显；候选池来自 BM25 词面召回（20 条几乎都含「小男孩/男孩」），强制全排列必然留下无关尾部。
- 第二版改为「发送 20 张缩略图做视觉复核 + 只返回相符编号」，无关尾部消失、负例可拒绝；但每次搜索要上传约 1MB 图片、输入 token 约 4.2k，且必须用多模态模型——对“排序”这件事是过度设计。
- 现版**不发送图片**：图片描述本来就是 VL 模型对画面的理解，重排只是“用查询去比对已保存的描述”，相当于人按文字描述找匹配条目，不需要再看原图。这样任何便宜/文本模型都能做，token 与延迟都显著下降。

**新链路**（勾选后，精确搜索与语义搜索共用）：

1. 候选取前 **20** 个（精确=BM25 top-20；语义=图像向量 top-20）；
2. 后端读取每个候选的 `vl_annotations` 结果文本（caption + tags）；**没有描述的候选不进请求**，原样作为 `unannotated` 返回；
3. 纯文本请求发给**设置页的「重排模型」**（与图片理解模型分开；默认 `zhipu/glm-4.6`，`LAP_VL_RERANK_MODEL` 仅作调试覆盖），`thinking: {"type":"disabled"}`、`temperature: 0`、`max_tokens: 1000`、超时 30s；
4. 提示词要求**只依据描述文字**判断，只返回相符编号（不是全排列）：显式的人物性别/人数/颜色/地点必须相符；缺次要道具不算不符；没有符合返回 `[]`；
5. 后端校验（未知/重复编号丢弃、空数组合法、全是未知编号视为坏答案并重试一次）；
6. 前端顺序 = 模型筛选结果 + 无描述候选（末尾），并显示「其中 N 张没有图片描述，未参与重排」；零命中显示「没有与描述相符的照片」；失败保留原始排序并显示原因。

**重排模型选型实测**（同一批 6 个用例：精确 top-20 / 负例 / 语义 top-7 / 生日蛋糕 / 雪地红衣 / 单候选）：

| 模型 | 结果 | 延迟 | 计价（网关 `/v1/models`） | 备注 |
|---|---|---|---|---|
| `zhipu/glm-4.6` | 全部正确（`[101]`/`[]`/6 张蛋糕…） | **0.7–1.2s** | prompt 0.6e-6、completion 2.2e-6 /token | 默认；约 1.9k 输入 token → **≈$0.0011/次** |
| `auto/deepseek-v4.1-flash` | 全部正确 | 1.2–5.0s | 未暴露 | 结果可用但更慢 |
| `raccoon/sn-sensenova-6-8-flash-lite` | **不可用** | 2–28s | 0（免费） | `thinking:disabled` 无效：仍产生 69–2726 thinking token；2/6 用例在 800 token 截断为空；加到 4000 token 后对精确查询返回错误的 `[]`，耗时 22–28s |

**与旧「全排列」实现的指标关系**：更早的 76 条查询评测（R@1 0.921→0.961）衡量的是“排序质量”，旧实现必须返回全部候选；现实现返回**子集 + 无描述候选**，R@3 不再与 R@1 可比，故不沿用该表，改为上表的端到端用例。

**代价与边界**：每次搜索约 1.9k 输入 token（约为视觉版的 45%）、1–2s、一次网关额度；不发送图片。描述本身若有误/缺失，重排会继承该缺陷——无描述的照片无法判断，只能放在末尾，不能保证零误报。
