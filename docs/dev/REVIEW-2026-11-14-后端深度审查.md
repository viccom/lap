## 🔴 P0-1 云端嵌入通道无超时 + 同步命令主线程 join：网关挂起即整个应用冻结

- 位置：`src-tauri/src/t_embed.rs:625`（及 558-585、735-757）
- 证据（已复核）：
  ```rust
  std::thread::spawn(move || {
      let client = reqwest::blocking::Client::new();   // 无 .timeout(...)
      ...call_cloud_embeddings(&client, ...)...
  }).join()                                            // 无限等待
  #[tauri::command] pub fn search_captions(...)        // 同步命令，主线程内联执行
  ```
- 问题：VL 链路所有 HTTP 客户端都有超时（180s/30s/15s），唯独嵌入通道没有。嵌入源为 cloud 时，主搜索入口 `search_captions` → 专用线程 blocking 请求 → 主线程 `join()` 无限等待。网关 TCP 建立但不应答（进程卡死/代理黑洞）时 **UI 永久无响应，只能杀进程**。`rebuild_caption_embeds` 同理。
- 建议：client 加 `timeout()`（与其余通道对齐）；命令改 `async` 或 `spawn_blocking`。
- 分类：fork 新增。

### P0-4 AI 标签写入置 dirty|=8 且生产代码永不清除：永久切断该文件的 sidecar 标签导入
- 位置：`metadata/xmp.rs:1010-1016`（触发器）× `t_vl_tags.rs`（afile_tags INSERT）× `merge.rs:173-179`（dirty&8 时非破坏导入直接跳过）
- 证据（已复核）：一次 VL 标注 → 该文件 `dirty|=8` 永久置位 → 用户之后在 Lightroom 改 sidecar 标签、lap 重扫**永远静默忽略**。生产无 `SET dirty=0`（唯一清位点在 `#[cfg(test)]`，已核实 t_tags.rs:370）；唯一的强导入模式 `ManualOverwrite` 生产零调用（xmp.rs:1992 的调用点也在测试模块内，已核实）。AI 活动切断了用户从 sidecar 获取更新的通路。

## 修复优先级建议

- **P0（一批修，含测试）**：P0-1 嵌入超时+async 化；P0-2 redact 统一；P0-3 导出过滤 AI 子树；P0-4 dirty 位清理。四条都是小 diff，且 P0-3/P0-4 直接关系「AI 不污染用户事实」的既有纪律。
- **P1 按性价比排序**：P1-7（一行校验防文件"消失"）→ P1-6/P1-8（迁移代价）→ P1-4/P1-16（首搜冻结）→ P1-1（EOS）→ P1-3/P1-2（资源/计费）→ 其余。
- **P2**：实现 run 清理、缩略图防呆、FTS 自愈时顺带。

## 值得肯定（balance）

1. **取消/排队/崩溃恢复状态机**（queued 取消与 take_ready 同互斥、worker 先 drop(slot) 再 pump、panic 由 unwind 释放 + supervisor 补终态）推演扎实，全程锁不嵌套、无死锁路径。
2. **api_key 全链路防护**（skip_serializing + 独立 sidecar + 三条恢复路径保留密钥 + 测试锁死）——密钥从未进入日志/错误串/命令响应（逐点验证过）。
3. **FTS 排除过滤保住 `bm25(files_fts,...)` 的 rowid-NOT-IN 写法**、权重有 113 查询实测依据、废弃方案留注释。
4. **XMP 解析器的输入面收窄**（16MiB/64 层/100k 节点上限 + 拒 DTD）与写回的 temp+fsync+排他发布，是全库工程质量最高的部分。
5. `set_text_model` 先装新模型→探测维度→失败完整回滚旧模型，是这批代码里最严谨的失败路径。
